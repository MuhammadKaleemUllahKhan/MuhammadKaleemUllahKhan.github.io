Secure & Robust LLMs

Securing Large Language Models: From Jailbreaks to Trustworthy Agents

June 20, 2026 9 min read Muhammad KaleemUllah Khan

For most of computing history, software did exactly what its code said, no more, no less. Large language models broke that assumption. They take instructions in plain language, blend them with whatever text they happen to read, and act on the mixture. That flexibility is precisely what makes them so useful, and precisely what makes them so hard to secure.

Secure and robust LLMs are increasingly part of my research, because the same questions I ask about federated and adversarial systems, who can be trusted, what leaks, and how things fail under pressure, all reappear here in a new and slippery form. This post maps the new attack surface and the defenses taking shape against it.

Why LLMs need a new security lens

A traditional program has a clean boundary between code (trusted instructions) and data (untrusted input). An LLM dissolves that boundary. Everything, your instructions, the user's question, a web page it retrieved, the contents of a document, arrives as one stream of text, and the model treats it all as potentially instructive. When a system also has memory, tools, and the ability to act (an agent), a clever string of text can become an action in the real world.

The hardest LLM security problem in one sentence: the model cannot reliably tell the difference between instructions it should follow and text it should merely read.

The new attack surface

Prompt injection

If SQL injection was the defining web vulnerability of its era, prompt injection is its LLM successor. The idea: hide instructions inside content the model will process, so it follows the attacker instead of you. In direct injection a user simply types something that overrides your intended behavior. The more dangerous indirect form plants instructions in a place the model reads later, a web page, an email, a PDF, a code comment, so that a normal-looking request ("summarize this page") quietly triggers hostile commands. For an agent with access to email or a shell, that is a serious problem.

Jailbreaks and adversarial prompts

Jailbreaks are inputs crafted to bypass a model's safety training, coaxing it into producing content it was aligned to refuse. Some are clever role-play; others are almost unreadable strings discovered by automated search. This is the LLM face of the adversarial examples I wrote about for vision models: a small, deliberate perturbation of the input that flips the model's behavior. The medium is text instead of pixels, but the underlying fragility, decision boundaries that sit closer than we would like, is the same.

Data poisoning and backdoors

LLMs are trained and fine-tuned on enormous, often loosely curated corpora. That opens the door to poisoning: an attacker who can slip crafted text into the training data can degrade the model or implant a backdoor, a hidden trigger phrase that makes the model misbehave on command while looking perfectly normal otherwise. Because the trigger is rare, it can survive evaluation and lie dormant until used.

Memorization and data leakage

Models sometimes memorize fragments of their training data verbatim, and the right prompt can pull those fragments back out, including secrets, personal information, or proprietary text. This is the privacy problem in a new guise: the model itself becomes a lossy archive of everything it was trained on, and extraction attacks try to read that archive.

What defense looks like

There is no single switch that makes an LLM safe. As with privacy and robustness elsewhere, real security comes from layers that each assume the others might fail.

  • Alignment training. Techniques such as reinforcement learning from human feedback teach the model to refuse harmful requests in the first place. Necessary, but never sufficient on its own, alignment can be jailbroken.
  • Input and output guardrails. Separate classifiers screen prompts for known attack patterns and screen responses for unsafe or leaking content before anything reaches the user or a tool.
  • Grounding and retrieval. Anchoring answers in a trusted, retrieved knowledge base reduces hallucination and gives you a verifiable source, though the retrieved content must itself be treated as untrusted to avoid indirect injection.
  • Least privilege for agents. The most reliable defense is often architectural: give an LLM agent the narrowest possible access, require confirmation for consequential actions, and never assume its output is safe to execute blindly.
  • Adversarial testing and red-teaming. Systematically attack your own model before someone else does. You cannot patch a jailbreak you have never tried to write, the same principle that drives adversarial training for classifiers.
A useful mindset: treat every byte the model reads, and every byte it writes, as untrusted until proven otherwise. Security comes from the system around the model as much as from the model itself.

The distributed angle

This is where my own research threads converge. Organizations increasingly want to fine-tune LLMs on sensitive, private data, medical records, internal documents, customer conversations, without centralizing it. That is a federated-learning problem wearing a very large hat, and it inherits every challenge from my earlier post: non-identical data across participants, communication cost (now enormous, given model size), and updates that can leak the very data they were meant to protect.

It also inherits the energy problem. Fine-tuning and serving these models is heavy, so doing it efficiently across distributed, resource-limited participants is a research question in its own right, which is why parameter-efficient methods that update only a small slice of the model are so attractive in this setting.

Stack the threats together and the goal of secure and robust LLMs in distributed settings comes into focus: models that can be improved collaboratively on private data, that resist prompt injection and poisoning, that do not memorize and leak what they were shown, and that keep all of this true even when some participants are dishonest. That intersection of robustness, privacy, and distribution is exactly the territory my work on fair and secure federated learning is heading into.

Toward language models we can rely on

LLMs are being handed real responsibility, reading our documents, writing our code, and increasingly acting on our behalf, faster than our security practices have matured. The encouraging part is that we are not starting from zero. The lessons from adversarial robustness, from privacy-preserving learning, and from distributed trust all transfer, even if the surface looks new. Making these models genuinely trustworthy is less about a single breakthrough and more about disciplined, layered engineering, and that is a challenge well worth the effort.
